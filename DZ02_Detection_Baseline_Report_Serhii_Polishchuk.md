## 1. Умови запуску

Усі параметри baseline зафіксовані нижче. Повторний запуск з цією конфігурацією та тим самим evaluation split відтворює експеримент.

| Параметр | Значення |
|----------|----------|
| **Модель** | YOLOv8n (`yolov8n.pt`) |
| **Джерело ваг** | Ultralytics YOLOv8n, pretrained на COCO |
| **Input resolution (imgsz)** | 640 |
| **Confidence threshold** | 0.25 |
| **IoU threshold (NMS)** | 0.7 |
| **Evaluation split** | val (VisDrone2019-DET-val, 548 зображень) |
| **Hardware** | GPU: Tesla T4 (Google Colab) |
| **Seed** | 42 |

### Підготовка даних

Використано той самий датасет VisDrone2019-DET, що й після Dataset Readiness Audit (ДЗ1).

Оригінальні анотації VisDrone  
(`x, y, w, h, score, category, truncation, occlusion`)  
сконвертовано у формат YOLO  
(`class x_center y_center width height`, нормалізовані 0–1).

- Клас 0 (ignored regions) та клас 11 (others) виключено.
- ID класів зсунуто на −1 (0…9): pedestrian, people, bicycle, car, van, truck, tricycle, awning-tricycle, bus, motor.
- Файл конфігурації: `visdrone.yaml`.

Модель **не донавчалася** на VisDrone — baseline є zero-shot оцінкою COCO-pretrained детектора на домені з дрона.

## 2. Baseline metrics

Результати валідації на **val** при `imgsz=640`:

| Метрика | Значення |
|---------|----------|
| **mAP50-95** (основна метрика курсу) | 0.0037 |
| **mAP50** | 0.0069 |
| **Precision** | 0.0789 |
| **Recall** | 0.0147 |
| **Peak GPU memory** | 274 MB |
| **Час валідації (val)** | ≈ 14.5 с |

### Інтерпретація

Метрики дуже низькі. Це очікувано для zero-shot переносу:
- COCO — зйомка з рівня землі / типових ракурсів;
- VisDrone — вид зверху, сильний scale variation, багато дрібних і щільно розташованих об’єктів.

Модель майже не знаходить об’єкти (низький recall) і дає багато хибних спрацьовувань відносно влучень (низький precision у абсолютних числах). Ці значення є **reference point** для подальшого error analysis і fine-tuning.

## 3. Аналіз за розміром

### Кількість GT-об’єктів на val (за розміром)

Розмір визначено як приблизну сторону бокса: \(\sqrt{w \times h}\) у пікселях (та сама схема, що в Dataset Audit):

| Категорія | Критерій | Кількість | Частка |
|-----------|----------|-----------|--------|
| **small** | side < 32 px | 26 586 | **~69%** |
| **medium** | 32 ≤ side < 96 px | 11 105 | ~29% |
| **large** | side ≥ 96 px | 1 068 | ~3% |
| **total** | — | 38 759 | 100% |

### Якість baseline за класами (mAP50-95)

| Клас | mAP50-95 |
|------|----------|
| pedestrian | 0.0297 |
| truck | 0.0059 |
| bus | 0.0006 |
| awning-tricycle | 0.0001 |
| motor | 0.0001 |
| people, bicycle, car, van, tricycle | 0.0000 |

### Висновок по small objects

- Більшість об’єктів на val — **дрібні** (~69%).
- Загальний mAP50-95 (0.0037) відображає саме цю складність: детектор, налаштований на «звичайні» розміри COCO, погано працює на small objects з дрона.
- Результат на small objects **суттєво гірший** за те, що можна було б очікувати на large objects; загальна метрика «тягнеться вниз» через домінування дрібних боксів.

Це обґрунтовує контрольовану зміну, спрямовану саме на small objects.

---

## 4. Контрольована зміна

| Поле | Зміст |
|------|-------|
| **Що змінили** | Input resolution: `imgsz` **640 → 1280** |
| **Чому** | ~69% об’єктів на val мають сторону < 32 px. Більший input дає дрібним об’єктам більше пікселів і має підвищити recall / mAP на small objects. |
| **Що залишилось без змін** | Модель і weights (`yolov8n.pt`), conf=0.25, iou=0.7, evaluation split=val, спосіб підрахунку метрик, seed |

Tiling **не** застосовувався. Змінено лише один фактор pipeline — input resolution.

## 5. Before / After

| Метрика | Baseline (imgsz=640) | Changed (imgsz=1280) | Зміна |
|---------|----------------------|----------------------|-------|
| **mAP50-95** | 0.0037 | **0.0110** | **+0.0074 (~3×)** |
| **mAP50** | 0.0069 | **0.0203** | ~3× |
| **Precision** | 0.0789 | 0.0832 | майже без змін |
| **Recall** | 0.0147 | **0.0428** | **~3×** |
| **Processing time (val, с)** | 14.5 | 10.5* | див. примітку |
| **Peak GPU memory (MB)** | 274 | **992** | **×3.62** |

\*Час повного прогону val може залежати від кешу; inference на один кадр при imgsz=1280 був помітно повільнішим (порядку ~10 ms vs ~3 ms на кадр у логах Ultralytics).

### Small-object quality (якісний висновок)

Окремого per-size mAP у звіті Ultralytics у цьому прогоні не виводилось чисельно для small/medium/large AP, але:
- загальний **recall** зріс у ~3 рази;
- **mAP50-95** зріс у ~3 рази;
- при домінуванні small objects на val (69%) основний внесок у зростання метрик логічно пов’язаний із кращим детектуванням дрібних об’єктів.

### Висновок експерименту

**Чи дала зміна вимірюваний вплив на метрики (зокрема в контексті small objects)?**  
Так. Збільшення `imgsz` з 640 до 1280 підвищило mAP50-95 і recall приблизно втричі при майже незмінному precision.

**Яка ціна для продуктивності?**  
Peak GPU memory зросла з 274 MB до 992 MB (у ~3.6 раза). Це суттєвий resource cost на Tesla T4. Для систем з обмеженою пам’яттю або real-time вимогами така зміна може бути неприйнятною без подальшої оптимізації (менша модель, TensorRT, tiling замість глобального upscale тощо).

**Підсумок:**  
Контрольоване збільшення input resolution — ефективний важіль для zero-shot baseline на VisDrone, де домінують small objects. Покращення якості вимірюване, але супроводжується помітним ростом споживання пам’яті. Цей baseline і результат зміни стають точкою відліку для error analysis, гіпотез покращення та fine-tuning на наступних етапах курсу.
